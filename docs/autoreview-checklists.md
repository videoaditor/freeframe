# Saved AutoReview checklists

Staff file requests containing a Trello URL resolve its canonical card through the existing private card verifier during asynchronous preparation. The creator must remain active staff before each unfrozen request read, including retries with an already verified card ID. Customers and deactivated/missing creators cannot use this route to read private Trello inputs. The verified card ID is saved separately from the immutable original intent; verification outages retry without changing the upload request. Once the snapshot is frozen, retries never reload the card or current rules. Previously failed staff requests can use the existing authenticated retry after deployment; no new request or duplicate upload is needed. Already verified internal Handin assignments retain their existing authorization path.

File requests save their original briefing and a preparation intent in the same transaction as the upload link. The link is immediately usable. Authorized staff can prepare a Trello assignment after choosing its workspace; preparation creates no folder. The eventual folder adopts that same binding, including on duplicate submissions or when adopting a matching older hand-in folder.

Handin shows a private collapsible checklist, source layer (Basics, Brand, Briefing), and whether a check applies per video, per variant, or to the whole submission. Share dialogs stay focused on copying/sending the link and do not show checklist content or status. Preparation is not a review or approval. Missing/failed preparation stays visible and can be retried. Guest upload responses and public card lookup contain no checklist or source text. The owner list rechecks current project access, including for former creators. Customer-provided Trello links do not grant the service account access: their preparation is unavailable; staff preparation uses a verified canonical card identity. A verified short-to-canonical card mapping lets older hand-in folders attach locally during a Trello outage.

Postgres owns the immutable intent, snapshot, context hash, plan reference, and retry status. Existing Celery/beat resumes committed work every minute. Plan and registration use independent retry counters and schedules; three failed registration attempts stop automatic retries until the authenticated retry endpoint is used. Deleted/revoked parents retire pending work. Every changed plan/context reference commits its pending registration marker before delivery. A snapshot is committed before any plan submission and is never reloaded after freezing. A timeout after Engine acceptance retries the same idempotency key and canonical bytes; the Engine must durably deduplicate them. Hashes use RFC 8785 with ASCII object keys and safe finite numbers; a shared fixture exercises Unicode, ordering and decimal rule values.

The optional Worker adapter is disabled unless `AUTOREVIEW_PLAN_API=on` and existing Engine service configuration is present. The proposed Engine POST/GET plan contract still needs owner confirmation. This PR does not implement a compiler or make the Engine consume the saved plan during review. Until that work is integrated, checklist-to-review reuse and live acceptance are unverified. Enabling the flag alone is insufficient. The flag does not disable snapshot resolution or PDF parsing, which may call the existing Gemini provider.

## Server-only frozen context read

`GET /internal/review/checklist-snapshot` accepts `share_token`, `project_id`, `asset_id` and `version_id`. The Worker prefixes this with its existing `FREEFRAME_BASE` (normally ending `/api`) and sends `Authorization: Bearer <FREEFRAME_BRIDGE_SECRET>`, matching FreeFrame's existing `REVIEW_BRIDGE_SECRET`. User JWTs, guest links and the separate read-only `X-API-Key` alone do not authorize this route. No new account rights or secret setting are introduced.

The endpoint requires the binding's exact live, public, unpassworded standing folder share; active project/folder/asset/version; matching tenant and asset/version association; and, for file requests, the same non-revoked request/folder/project/share association. This minimal read supports assets directly in the bound assignment folder. Other folders, including nested folders, receive no saved context. It verifies the stored canonical hash and snapshot identity before returning anything private. A saved snapshot remains readable when optional plan preparation is unavailable; readiness is not required and is not claimed.

The `autoreview.saved-snapshot.v1` response includes `tenant_id`, `binding_id`, nullable `upload_request_id`, `asset_id`, `version_id`, `version_number`, `context_sha256` and the unchanged full `snapshot`. Inside that snapshot, `request_id` means the binding ID. Responses use `Cache-Control: private, no-store`. The read never reloads current rules, resolves URLs, invokes providers, compiles a plan or changes retries. Disabled bridge returns 503; missing/wrong service auth 401; absent or mismatched scope/snapshot 404 (disabled/expired shares may return 403/410); corrupt snapshot 409. Consumers must verify echoed identities/hash and can continue their existing label-free review when no valid saved context is available. Private source text must stay server-side. This endpoint alone does not implement a Legacy or Engine consumer or prove native source labels.
